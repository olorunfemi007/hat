The important architectural decision is this: do not make the Raspberry Pi understand AWS, Azure, MinIO, GCP and every customer's storage system.

It could be written in Go, Rust, or Python. Given your infrastructure background, I'd strongly consider Go because you can distribute one binary, it is lightweight, handles concurrency well and is good for long-running device agents.

2. Don't send video through the same pipeline as sensor metrics

This is an important distinction.

Humidity might generate a message like:

{
  "device_id": "HAT-A73F92",
  "timestamp": "2026-09-05T15:32:10Z",
  "humidity": 74.2,
  "temperature": 31.4,
  "fan_rpm": 2200,
  "battery": 71
}

That is tiny.

Send those messages using something like:

MQTT over TLS

MQTT is extremely common for IoT devices and Azure IoT and AWS IoT both support MQTT-based device communication/provisioning. AWS IoT, for example, supports device certificate provisioning through MQTT; Azure's Device Provisioning Service is specifically designed for zero-touch IoT provisioning at scale.

But video is different.

You don't want:

Camera
  ↓
MQTT
  ↓
10 GB video

Instead:

Camera
   ↓
H.264/H.265 encoding
   ↓
30–60 second segments
   ↓
local disk buffer
   ↓
HTTPS upload
   ↓
Object Storage

So your system has two data planes.

                 Hard Hat
                    │
           ┌────────┴────────┐
           │                 │
     TELEMETRY PLANE     MEDIA PLANE
           │                 │
          MQTT             HTTPS
           │                 │
       MQTT broker        Object store
           │
      stream processor
           │
        database
3. Make S3 your primary storage abstraction

This would probably be one of the most important decisions for making your product generic.

Build an interface internally like:

type ObjectStore interface {
    PutObject(...)
    GetObject(...)
    DeleteObject(...)
    GenerateUploadURL(...)
}

Then implementations:

S3Storage
AzureBlobStorage
GCSStorage
MinIOStorage
NFSStorage

But make S3-compatible storage your preferred interface.

That immediately gives you compatibility with things such as:

AWS S3
MinIO
Ceph
Cloudflare R2
Wasabi
many enterprise object-storage systems

For AWS S3 specifically, presigned URLs allow a device to upload an object without giving the device the customer's AWS credentials.

That is exactly the pattern I would use.

4. Never put customer cloud credentials on the hard hat

Suppose Company A uses AWS.

You should not put:

AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY

on every Raspberry Pi.

Instead:

Hard Hat

"Hey backend, I have:
 video-20260905-153200.mp4
 82 MB"

       ↓

Your Gateway

       ↓

Customer's S3 configuration

       ↓

Generate temporary upload URL

       ↓

Hard Hat receives:
https://company-bucket.s3...signed...

       ↓

Hard Hat uploads directly to S3

The signed URL expires shortly afterwards.

The device never learns the AWS credentials. AWS explicitly supports this pattern for uploads using time-limited presigned URLs.

Now your backend also doesn't have to proxy enormous quantities of video.

That is a big scalability advantage.

11. Local buffering is extremely important

Construction sites and mines will lose Wi-Fi.

The helmet therefore needs an edge queue.

For example:

                 Internet available
                       │
                       ▼
Sensor → Agent → Upload

                 Internet unavailable
                       │
                       ▼
Sensor → Agent → local SQLite / disk

                       │
                  Wi-Fi returns
                       │
                       ▼
                 Retry uploader
                       │
                       ▼
                     Cloud

The Pi could have:

64–256 GB SD / NVMe

and maintain a queue:

pending/
uploading/
uploaded/
failed/

Telemetry could sit in SQLite until acknowledged.

Video could stay on disk until uploaded.

This means losing Wi-Fi doesn't mean losing evidence.
